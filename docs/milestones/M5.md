# M5 — Reminder loop

> One file per milestone: **Plan** (approved at STOP 1) on top, **Results** (STOP 2) below.

## Plan

**Branch:** `feature/M5-reminder-loop` · **Time box:** 5 h, built in two halves (Decision 1) · **Status:** approved 2026-11-03 (STOP 1, all recommendations; prompt texts still need his approval) — building 5a · **Then:** CP2 full review, then M6

### Goal

Close the loop from "who owes me" to "Asha called and here's what happened". Srinivas gets a due alert on WhatsApp and taps **Remind** for one person, or **Remind all due**. Ramesh's phone page rings; everyone else gets a **simulated** text call. Asha now **remembers** the last promise and gets **firmer** after broken ones. After every call, a **follow-up agent** writes a note and sends Srinivas a WhatsApp summary with buttons where he must act. Promises are checked for **kept / broken**, and every shopkeeper gets a **reliability score**.

### Acceptance criteria (SPEC §17 M5 = demo steps 2–6, §6.4, §6.5, §7.3, §7.4, §7.7, §8, §9)

- **Due alert:** "who is due?" and a daily message list who is due today, who is overdue and who broke a promise. There is a **Remind** button per person (buttons for ≤3 people, a list of up to 10 for more). Nobody is called unless Srinivas picks them
- **Remind all due** → "Call 7 people?" [Yes] [No] → the live shopkeeper rings; the rest are simulated, at most 4 at once
- **Memory:** Asha opens the money talk with the last promise (amount, date, kept or broken), the last call note and any rejected claim
- **Tone ladder:** level 1/2/3 worked out in code from broken promises and days overdue, and passed to Asha. No threats at any level. The level-3 consequence is said only if Srinivas set one
- **Follow-up agent:** after every call, live or simulated: rules for clear cases, the LLM only for judgement calls, a note always written, and a WhatsApp summary (outcome, promise or claim, tone level, next step, "simulated" label) with [Confirm received] [Not received] when a claim was made
- **Promise checker:** a promise whose date passed without enough confirmed payment → **broken**; paid in time → **kept**
- **Reliability score:** 0–100 from the 4 parts in SPEC §9, with bands; shown in "pending", "Ramesh" and summaries; "why is Ramesh 42?" explains it
- **Done when:** the smoke test below passes on Saim's phone and Chrome

### How the loop works (new in M5)

```
Daily (pg_cron, 9:00 IST on the demo clock) or "who is due?" ──► due alert on WhatsApp
   [Remind Ramesh] / list pick / [Remind all due] → "Call 7 people?" [Yes]
        │
        ├─ live shopkeeper (Ramesh) ─► `calls` row queued ─► /phone rings (M3) ─► Asha on Sarvam
        │                                   get_dues now also returns memory + tone level
        │     hang-up → /ended → follow-up queued
        │
        └─ others ─► simulated call: Asha's prompt + tools on sarvam-105b (text) vs a persona LLM
                     max 4 at once; same tools, same rules, same audit rows; transcript in hand
                            │
   follow-up worker (runs after each call; pg_cron sweeps every minute for stragglers):
     transcript (live: Sarvam Analytics API, retried while it lags) → rules → LLM if unclear
     → note (Asha reads it next call) → followups row → score recalculated
     → WhatsApp summary to Srinivas (+ claim buttons)
Promise checker: before every alert, every get_dues and once a day → open promises → kept/broken
```

#### Decision 2: How Asha gets memory and tone — ⚠️ prompt change (your decision)
📐 `get_dues` (already called right after identity) also returns `last_promise`, `last_note`, `rejected_claim`, `tone_level` and, at level 3 only, the owner's consequence text. The level is worked out in **code**:

| Level | When (SPEC §7.4) |
|---|---|
| 1 Friendly | No broken promise and under 15 days overdue |
| 2 Firm | 1 broken promise, **or** 15+ days overdue |
| 3 Firmer | 2+ broken promises (last 6 months), **or** 30+ days overdue |

📐 **Asha prompt v3** adds one short "Memory and tone" section: how to raise the last promise naturally, and one line of how to sound per level. The never-list stays. I show you the exact text during 5a, before it goes to Sarvam (as with v2). The level is stored on the call and shown in the summary.
✅ **My recommendation:** as above. Ramesh's seeded broken ₹3,000 promise puts him at **level 2**, which is exactly the demo moment ("Last time you said Friday for 3,000 rupees…").

#### Decision 3: When is a promise kept or broken?
📊 **Options:** (a) **kept** if confirmed payments made between the promise and its date (+1 day grace) add up to the promised amount; otherwise **broken** the day after the grace day. A part payment still counts as broken, but the summary says "paid ₹1,000 of ₹3,000" · (b) a part payment counts as kept.
✅ **My recommendation:** (a). Clear and simple to explain; the score already rewards part payments through "current overdue".
📐 **No separate scheduler needed for correctness:** the check runs before every alert and every `get_dues`, and once a day. Running it twice changes nothing. It uses the **demo clock**, so in the demo you move the clock forward and see a promise break.

#### Decision 4: Follow-up agent: rules first, LLM second — ⚠️ prompt (your decision)
📐 **Rules** (no AI) handle the clear cases:

| Call result | Next step |
|---|---|
| Promise logged | Check on the promise date |
| Claim recorded | Ask the owner: [Confirm received] [Not received] |
| Owner callback asked | "Please call Ramesh: <reason>" |
| Declined / no answer | "Didn't answer. [Try again]" |
| Wrong person | "Someone else answered; nothing shared" |

📐 **LLM** (`sarvam-105b`, Gemini fallback) only when signals are mixed: no promise, hardship mentioned, an angry call, or a promise *and* a dispute. It picks one of: remind again on a date / owner should call / pause reminders, and gives a one-line reason. It returns checked JSON, as in M4. Its prompt is shown to you during 5a.
📐 **Always** a note of 1–2 lines for Asha's next call, from the transcript. Every run is stored in `followup_runs` with its path (rule/agent), so CP2 and M7 can audit it.
✅ **My recommendation:** as above.

#### Decision 5: Live-call transcript
🔍 The phone page reports Sarvam's interaction id at hang-up (built in M3). The Analytics API can lag a few minutes behind the call.
📊 **Options:** (a) try at once, then retry every minute for up to 10 minutes (pg_cron sweep). The summary goes out as soon as the transcript arrives, or after 10 minutes from tool events alone, marked "transcript not available" · (b) send the summary from tool events at once, without a transcript.
✅ **My recommendation:** (a). The note needs the transcript to be useful; the tool events guarantee a summary anyway.

#### Decision 6: Simulated calls — ⚠️ persona prompt (your decision)
📐 Asha's **same prompt (v3) and same 5 tools** run in text on `sarvam-105b`; the tools go through the same code path, rules and audit rows. The shopkeeper is played by a second LLM from the seeded persona (cooperative, slow payer, claims paid, disputes, hardship, son answers…).
📊 **Who plays the shopkeeper:** (a) **Gemini** (a different model, so the two sides don't mirror each other) · (b) `sarvam-105b` too.
✅ **My recommendation:** (a) Gemini for the shopkeeper, Sarvam for Asha, so Sarvam is the one being shown off. Max 10 turns per call. Each call runs in its own background run, so a batch never hits the function time limit. Every simulated call is labelled **simulated** in summaries and the dashboard. You see the persona prompt during 5b.
💰 About ₹1 per simulated call (~20 LLM calls). A "remind all" of ~10 people ≈ ₹10.

#### Decision 7: The daily alert and WhatsApp's 24-hour rule (R1) — ⚠️ creates a Meta template
🔍 WhatsApp lets a business send free messages only within 24 hours of the owner's last message. A 9 am alert usually falls outside that.
📊 **Options:** (a) **template fallback**: inside 24 h → the full alert with buttons; outside → a short approved utility template, *"Good morning. 7 shopkeepers are due today. Reply DUE to see them."* His reply opens the window and gets the full alert · (b) on-demand "who is due?" only, no daily message (SPEC cut order item).
✅ **My recommendation:** (a). I create the template on your test WhatsApp account through the API (a setting change on your Meta account; I ask before doing it). Meta usually approves utility templates within minutes. If it's refused or slow, the daily message falls back to (b) for the demo, and "who is due?" always works.

#### Decision 8: Queue and limits
📐 Only **one live call** at a time (one phone page); others wait as `queued` and ring after it ends. **Up to 4 simulated calls** run at once; the rest wait, and the cron sweep starts the next one. The pre-call check from M3 (do-not-call, switchable hours and limits) applies to every reminder. A shopkeeper already called in the last hour is skipped from "remind all", and the confirmation says so ("6 to call, 1 called recently").
✅ **My recommendation:** as above.

#### Decision 9: Reliability score
📐 Exactly SPEC §9, in code, 100% tested: paid on time 40, promises kept 30, current overdue 20, answers calls 10. Bands: Reliable 75+, Watch 50–74, Risky <50, **New** if fewer than 3 credits or under 30 days of history. Recalculated after each confirmed payment, call and promise check; stored on `shopkeepers` (score + parts). "why is Ramesh 42?" (or "Ramesh score") returns the four parts in one line each.
✅ **My recommendation:** as above.

### Plain-English notes (for the pitch)

- **Why the tone level is set in code:** the AI never decides how hard to push. A rule does (broken promises, days overdue), so it's fair, the same for everyone, and explainable to a regulator.
- **Why a simulated call uses Sarvam for Asha and Gemini for the shopkeeper:** two different models talking avoids an AI agreeing with itself, and Asha, the product, stays on Sarvam.
- **Why the score is not AI:** a shopkeeper's reputation shouldn't come from a black box; four plain numbers explain every score.

#### Sarvam transcript API shape (read-only GETs, 2026-11-03)

```
GET https://apps.sarvam.ai/api/analytics/v1/{org}/{workspace}/{app}/transcripts/{interaction_id}
X-API-Key: SARVAM_AGENTS_API_KEY
→ { interaction_id, messages: [{ turn_id, role: "assistant" | "user", content, language_name }] }
  404 or empty messages = not ready yet (worker retries)

GET …/{org}/{workspace}/{app}/interactions?start_datetime&end_datetime
→ { items: [{ interaction_id, agent_variables: { call_token, … }, … }], total, … }
```

#### Deviations

- **Remind all is capped at 10 people** per tap (budget guardrail, about ₹1 per simulated call). The confirmation says how many were left out.
- **Who is live:** the shopkeeper set for the phone page in demo settings (Ramesh) gets the one live call; everyone else gets a simulated call. A second live reminder waits as `queued` until the first ends.
- **Same name for two shopkeepers:** the bot lists their shop names and asks again (no pick card for Remind).
- **"remind X" / "X score" with an unknown name** goes to the LLM brain, like an unknown name in M4.
- **The webhook wakes the worker's sweep after each owner message.** A cheap fallback if pg_cron is off or late.
- **The 4-at-once limit is enforced in the database** (`claim_simulated_call` with an advisory lock), so two worker runs can never both start a fifth call. A simulated call stuck in progress for over 5 minutes is ended and followed up from its tool events.
- **The shopkeeper side falls back to Sarvam** if Gemini fails (free tier is about 10 requests a minute). The log records which side failed.
- **Template is English only** (one Meta template). The full alert after "DUE" is in the owner's language.
- **Nobody due → no daily message** (no "all clear" template).
- **Personas:** the seed has 4 (`cooperative`, `slow_payer`, `avoids_commitment`, `new_customer`). The prompt also has 4 unseeded ones (claims paid, disputes, hardship, son answers) for M7's evals.
- **Asha in text needs a short text-mode section** (reply as JSON, how to call a tool). Asha's v3 prompt itself is used unchanged; the section is a draft for Saim.
- **The promise check runs at 08:45 IST,** 15 minutes before the alert, so the alert sees today's broken promises.
