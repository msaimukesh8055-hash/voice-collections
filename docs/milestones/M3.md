# M3 — Sarvam switch + ledger

> One file per milestone: **Plan** (approved at STOP 1) on top, **Results** (STOP 2) below.

## Plan

**Branch:** `feature/M3-sarvam-ledger` · **Time box:** 4 h · **Status:** approved 2026-11-02 (STOP 1, all recommendations incl. 60-min voice budget) — building · **Then:** M4 (WhatsApp core)

### Goal

Move Asha from Vapi to **Sarvam Voice Agents** and give her a real credit book to work from. Srinivas Reddy's ledger (1 owner, 100 fake shopkeepers, 6 months of history) replaces the Suvidha loan tables. Asha calls through a **borrower phone page** that rings like a real phone. She uses 5 tools that run on our server, follow the rules in code and write an audit row each time. The browser never holds the Sarvam key.

### Acceptance criteria (SPEC §17 M3)

- A **30-minute spike** runs first and passes its go/no-go checks (Decision 1) before anything else is built
- New schema + seed: 1 owner, 100 shopkeepers, 6 months of credits/payments/promises spread across score bands; old Suvidha tables gone
- Asha on Sarvam with the 5 tools: `confirm_identity`, `get_dues`, `log_promise` (once per call), `record_payment_claim`, `request_owner_callback`
- No amount is ever given before identity is confirmed (code + test + audit row); a payment claim never reduces the balance
- `/phone` page: rings, Accept/Decline, Sarvam call, two avatars with who-is-speaking animation, live transcript
- **Done when:** a live Chrome call to Ramesh uses the real tools against the new ledger

### How one call works (new in M3)

```
Dashboard "Ring Ramesh" ── POST /v1/demo/ring ──► calls-api
                 pre-call check (do-not-call; hours/limits only if switched on) → `calls` row: queued
/phone (asks every 2 s) ── GET /v1/phone/incoming ──► rings: "Sri Lakshmi Traders" [Accept] [Decline]
Accept ── POST /v1/calls/{token}/accept ──► language, greeting, names, call token
Sarvam SDK ── "give me a call URL" ──► calls-api proxy (holds SARVAM_API_KEY) ──► Sarvam → signed URL
Browser ⇄ Sarvam: audio both ways, direct (our server is not in the audio path)
Sarvam ── POST /sarvam-tools/<tool> + secret + { call_token, interaction_id, args } ──► sarvam-tools
          check secret → find call by token → lock to this Sarvam call → validate → guard
          (identity confirmed?) → run → audit → reply
Hang up ── POST /v1/calls/{token}/ended { interactionId, seconds } ──► `calls` row: completed
```

*Signed URL = a one-time web address that lets the browser open the audio connection without the API key. Proxy = our server makes that one request on the browser's behalf.*

#### Decision 2: Server region (R4) — ⚠️ needs Saim's decision if we move
🔍 Our database and functions are in **Oregon** because Vapi was there (ADR-0008). Sarvam's servers appear to be in **India** (its published tool IPs belong to Indian cloud regions; confirmed in the spike). Every tool call would cross the Pacific. M2 measured ~0.5 s from India to Oregon.
📊 **Options:** (a) **stay in Oregon** and pin functions there with a fixed `x-region` header on every Sarvam tool, one ocean crossing per tool call · (b) **new Supabase project in Mumbai** (ap-south-1). Tool calls stay inside India (~0.1–0.2 s expected). The free plan allows 2 active projects, so the Oregon project is **paused** (reversible, its data kept). ~20 min: create, `db:push`, deploy, new keys in `.env`.
✅ **My recommendation:** decide by the spike number. **Sarvam p50 ≤ 500 ms → stay. Above 500 ms → move to Mumbai.** I expect a move.
📐 **Reasoning:** SPEC R4 allows up to 1 s, but each tool call is silence on top of a ~2 s turn, so 500 ms is the line I'd defend. M3 rebuilds the database anyway, so this is the cheapest moment to move. Moving also means **no Suvidha table is dropped** (the new project starts empty) and the pitch can say "data stays in India", matching Sarvam's own residency story. ADR-0008 gets amended either way.

#### Decision 3: How Sarvam's tool calls reach us (`sarvam-tools` replaces `vapi-webhook`)
📊 **Options for the secret:** (a) Sarvam's built-in **bearer auth**: the secret sits in Sarvam's Secrets vault and is sent as `Authorization: Bearer …` · (b) secret typed into the tool body (visible in the agent config: no).
📊 **Options for the call token:** (a) **agent variable** `call_token`, seeded by the browser at call start, put in the request **body**, with Sarvam's "send to LLM" switch **off** so the model never sees it · (b) in a header (also works, but the body is easier to test and log safely) · (c) `user_identifier` (spike fallback only).
✅ **My recommendation:** bearer secret (a) + body token (a). One function, **one URL path per tool** (`/sarvam-tools/get_dues`, …). The tool name comes from our config, not the AI, and Sarvam's analytics show latency per tool. A fixed `x-region` header is added if we stay in Oregon.
📐 **Reasoning:** it reuses everything that passed CP1: constant-time secret check, token lookup, typed tool map, Zod validation, audit row, safe failures (ADR-0002). Only the request shape changes. The token locks to Sarvam's **Interaction ID** on first use (same pattern as the Vapi call id, ADR-0009), and that is also how we capture the interaction id (Decision 8). Even a leaked token is useless without the secret. Saim pastes `SARVAM_TOOL_SECRET` into Sarvam's Secrets page once (masked input), unless the MCP connector can set it.

#### Decision 4: Guarding the key proxy
🔍 An open proxy would let anyone with our public anon key start Sarvam calls on our credit.
✅ **My recommendation:** the proxy route only works with a **call token that was just accepted on the phone page**. It issues **one URL per token**, only for our own org/workspace/app ids (from server env), and returns `{ url }` and nothing else. The key goes only to Sarvam. No login, as before (fake data; known gap, real deployment adds owner login).
📐 One call token = one Sarvam session = at most one billed call, capped at 4 minutes by Sarvam's max call length.

📐 **New tables (SPEC §13):** `owners` · `shopkeepers` (incl. score + parts columns, empty until M5) · `ledger_entries` (credit/payment; status confirmed/claimed/rejected) · `promises` (open/kept/broken/replaced) · `calls` (token, live/simulated, status queued→ringing→in_progress→completed/declined/missed, interaction id, identity flag, tone level, transcript, timings, cost) · `tool_events` · `shopkeeper_notes`, `followup_runs`, `followups` · `eval_runs`, `eval_results`, `publishes` (+ Sarvam version, eval run optional until M7) · `demo_settings` (+ live shopkeeper) · `balances` view. #### Decision 7: Seed: how 100 shopkeepers and 6 months of history are made
📊 **Options:** (a) hand-written SQL (too big to write by hand) · (b) **TypeScript generator with a fixed random seed → `seed.sql`**, committed · (c) generate at run time in the database

#### Decision 8: How the phone page knows a call is waiting, and what we capture
📊 **Options:** (a) **polling**: the page asks the server every 2 s "any call for me?" · (b) Supabase Realtime (instant push), but the browser would need permission to read a table, which breaks our "no browser access" rule

The spike checks the transcript API works so M5 has no surprise.

#### Decision 9: Tool rules — ⚠️ needs Saim's decision (product policy)
| Tool | Proposed rule |
|---|---|
| `confirm_identity` | Asha reports the answer to "Are you Ramesh garu of Ramesh Kirana?": **confirmed / denied / unsure**. Confirmed → amounts allowed for the rest of the call. Asking again returns "already confirmed, don't ask again" (fixes the *identity question restarting* seen in testing). **Denied → locked for this call**: no amounts, end politely. Unsure twice → treated as denied |
| `get_dues` | Refused until confirmed. Returns total outstanding, overdue amount, oldest due date, days overdue. Counts **confirmed** entries only. Also returns `memory: null`, `toneLevel: 1` (placeholders filled in M5) |
| `log_promise` | Amount **₹100 to the full outstanding** (part payments fine), date **today to +14 days**. A second call in the same call **returns the saved promise** instead of saving another (fixes the *duplicate promise*) |
| `record_payment_claim` | Amount up to the outstanding, paid date in the last 30 days, mode cash / UPI / bank transfer / cheque. Saved as **claimed** and **never** changes the balance. Once per call |
| `request_owner_callback` | Reasons: dispute / hardship / wants owner / other, plus a one-line summary. Works **before** identity too (a son can ask Srinivas garu to call), but shares nothing |

✅ **My recommendation:** as above. Old M2 rules (DOB, 50% minimum, payment links) are gone: a trader taking ₹2,000 of ₹8,500 is normal *udhaar*.

#### Decision 10: Asha prompt v1 and greeting — ⚠️ needs Saim's decision (prompts are yours)
**Greeting** (sent as the call's first message, built per call from the database):
- **Telugu (default):** "నమస్కారం, నేను ఆశ, శ్రీ లక్ష్మి ట్రేడర్స్ తరఫున మాట్లాడుతున్న AI అసిస్టెంట్‌ని. మీరు రమేష్ కిరాణా రమేష్ గారేనా?" *(Namaskaram, nenu Asha, Sri Lakshmi Traders tarafuna matladutunna AI assistant-ni. Meeru Ramesh Kirana Ramesh gaarena?)*
- **English:** "Namaste, I'm Asha, an AI assistant calling for Sri Lakshmi Traders. Am I speaking with Ramesh garu of Ramesh Kirana?"
- **Hindi:** "नमस्ते, मैं आशा हूँ, श्री लक्ष्मी ट्रेडर्स की तरफ़ से AI असिस्टेंट। क्या मैं रमेश किराना के रमेश जी से बात कर रही हूँ?"
- **After confirmation (Telugu):** "ధన్యవాదాలు. ఈ కాల్ రికార్డ్ అవుతోంది. రెండు నిమిషాలు మాట్లాడొచ్చా?" *(Thank you. This call is recorded. Can we talk for two minutes?)* Same in English/Hindi.
- ⚠️ The Telugu should be checked by a native speaker before the demo.

**Prompt outline (v1, for your approval; the full text comes back to you before the first push):**
1. **Who:** Asha, a polite AI assistant for Srinivas Reddy's shop, calling about *udhaar* (store credit). Warm, short sentences, "garu"/"ji", never threatening
2. **Identity first:** ask once → `confirm_identity`. Never repeat once confirmed. Wrong person → apologise, share nothing, end
3. **Recording notice**, then `get_dues`. Say figures **only** from the tool, exactly once. **No filler after a tool reply** (no "let me check" once the answer is in; fixes *filler after a tool result*)
4. **Promise:** agree amount + date → `log_promise` once → read it back ("₹3,000 on Monday, 9 November, correct?")
5. **"Already paid":** amount, date, mode → `record_payment_claim` → "I'll ask Srinivas garu to confirm". Never say the balance went down
6. **Dispute / hardship / wants the owner:** `request_owner_callback`, calm, no pressure
7. **Language:** start in the shopkeeper's language (Telugu for Ramesh), follow the speaker (Telugu / Hindi / English / mix)
8. **Never:** threats, shaming, mentioning family or others, figures not from a tool. (Tone ladder and memory slots are added in M5)
9. Thank, one goodbye, end the call

### Plain-English notes (for the pitch)

- **Why a proxy for the key:** the browser only gets a one-time call address; the key that can spend money never leaves our server.
- **Why rules in code:** "no amount before identity" and "one promise per call" are refused by the server, and the promise rule is also enforced by the database. The prompt says it too, but the AI can't talk its way past the code.
- **Why claims don't touch the balance:** only the owner closes an entry. Asha records what she heard; Srinivas confirms what he received.
