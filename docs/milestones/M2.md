# M2 — Platform core + collections tools + compliance

> One file per milestone: **Plan** (approved at STOP 1) on top, **Results** (STOP 2) below.

## Plan

**Branch:** `feature/M2-platform-tools` · **Time box:** 1 h 30 · **Status:** done — voice tested, gate passed (STOP 2: commit) · **Then:** CP1 (full review + score)

### Goal

Give Asha real tools. During a live call she can verify the borrower, read their dues from our database, log a promise to pay, send a (fake) payment link, and hand over to a human. Every tool runs on **our server**, checks the rules in code, and leaves an audit row. Calls are blocked before they start if they break calling rules.

### Acceptance criteria (SPEC M2)

- A voice call verifies the borrower, states the **seeded** dues, and logs a promise (row appears in `promises`)
- Loan details are **provably refused** before verification (test + audit row + live attempt)
- Compliance engine (calling hours, attempt limits, do-not-call) and tool guards: tests written first, 100% coverage
- Every tool call is checked against the shared secret, its arguments are validated, and it is audited in `tool_events`

### How one call works (new in M2)

```
Dashboard page ── POST /v1/calls/authorize (customer) ──► calls-api
                     pre-call check: hours · attempts · do-not-call
                     ✔ creates a `calls` row → returns call token + name + language
Browser ── vapi.start(assistant, { metadata: { callToken }, variableValues: { customerName } })
Vapi ── tool call + secret header ──► vapi-webhook
                     check secret → find call by token (never trust the LLM for identity)
                     → validate args → guard (verified? within policy?) → run → audit → reply
```

### Decisions

#### Decision 1: How the server knows who is on the call
📊 **Options:** (a) browser sends the customer id in call metadata · (b) browser first asks our API to **authorise** the call; the API runs the pre-call check, creates a `calls` row and returns its id as a one-time **call token**; the webhook looks up the customer from that token and locks it to the first Vapi call that uses it.
✅ **My recommendation:** (b)
📐 **Reasoning:** the pre-call compliance check can't be skipped (no token, no tools), and the customer can't be swapped mid-call. (a) is quicker but lets anyone start a call "as" any customer (they'd still need the date of birth, but it's weaker).

#### Decision 2: Calling rules — ✅ decided by Saim
- **Calling hours 08:00–19:00 IST** and **do-not-call**: always on (real compliance rules). "Now" comes from the **demo clock** when set, so a blocked 9 pm call can be shown on demo day.
- **Attempt limits** (3 per day, 7 per week): built and tested as a rule, but **off by default** through a demo switch (`demo_settings.call_limits_enabled = false`), so testing never hits them. Can be switched on to demo the rule.

#### Decision 3: Promise-to-pay policy — ✅ approved by Saim
✅ **Rule:** promise date **today to +10 days**; amount **at least 50% of the overdue, at most the full overdue**; modes: UPI, net banking, debit card, branch. Payment links: amount ≤ overdue.
📐 Outside these, the tool refuses and tells Asha why ("date must be within 10 days"), so she can renegotiate instead of guessing.

#### Decision 4: Temporary test prompt and greeting — ✅ decided by Saim
Asha needs instructions to use the tools. This is a **short functional prompt for M2 testing only**; the real one (persona, objectives, few-shots, Hindi examples) is written in M3 for Saim's review.
- **Greeting (casual, Saim's wording):** "Hi, I'm Asha, an AI caller from Suvidha Finance. Am I speaking with {{customerName}}?"
- **Right after the person is confirmed:** "Great! Quick heads-up, this call is recorded. Can I have a couple of minutes of your time?" — the recording notice **stays** (RBI expectation; SPEC §9) but moves out of the greeting, so a wrong person never hears more than the company name. Hindi follows the same casual tone.
- **Test change:** the greeting test now checks AI disclosure + name confirmation; a new prompt test checks the recording notice is given right after confirmation.
- **Prompt (summary):** confirm the person → if wrong person, apologise and end, reveal nothing · give the recording notice and ask for a couple of minutes · ask date of birth → `verify_customer` · never share any loan detail before verified · after 2 failed attempts, end politely · once verified, `lookup_loan` and state overdue + due date using only tool figures · if they'll pay: amount, date, mode → `log_promise_to_pay`, offer `send_payment_link` · dispute / wants a human / stuck → `transfer_to_human` · short, polite, never threatening, reply in the caller's language.

#### Decision 5: Dashboard API protection (prototype)
✅ **My recommendation:** no login for now. `calls-api` only lists customer names/language/city and authorises calls; all data is fake. Logged as a known gap (real deployment: Supabase Auth for collection agents).

#### Decision 6: Server location — lowest latency — ✅ requested by Saim
🔍 **Finding:** Vapi's call servers run in **AWS us-west-2 (Oregon, USA)** (from our call records). Our Supabase project is in **eu-west-1 (Ireland)**, so every tool call crosses the Atlantic (~140 ms per round trip, several per tool).
📊 **Options:** (a) stay in Ireland, run the webhook next to the database → one Atlantic crossing per tool call (~150–250 ms added) · (b) **new Supabase project in us-west-2 (Oregon)**, next to Vapi → tool calls stay inside one data-centre region (~20–60 ms added) · (c) Mumbai → worse (~230 ms per crossing, because Vapi itself is in the US)
✅ **My recommendation:** (b) Oregon.
📐 **Reasoning:** the slow part is the distance between Vapi and our data, and Vapi can't be moved. Schema and seed are already scripted, so moving takes ~15 minutes. The free tier allows only **two active projects**, and iInspect uses one, so the Ireland voice project must be **paused** (reversible) before the Oregon one can be created.
⚠️ **Honest trade-off (interview point):** a real Indian NBFC would need data stored in India (RBI data localisation). That only gets low latency if the voice platform also runs in India, so production would need a voice provider with an Indian region. Recorded in a new ADR-0008; ADR-0003 updated.
✅ **Done 2026-11-01:** Ireland project paused; `voice-collections-us` created in us-west-2; schema + seed applied; seed check passed (9/9 tables, anon key blocked).

|---|---|

| Supabase access token expires mid-milestone | Checked today: works. If it expires, you create a new short-lived one |

### Plain-English notes (for interviews)

- **Why rules in code, not the prompt:** an LLM can be talked out of an instruction; a server that refuses to return loan data until verified can't. The prompt says it too (defence in depth).
- **Why a call token:** the server decides who the customer is, before the call, after the compliance check — the AI never gets to say "I'm talking to Ravi".
- **Why one webhook and a tool map:** security check, validation and audit are written once and tested once; adding a tool means adding one entry.

### Small decisions made while building (flag if you disagree)

- **End-call tool added:** without it Asha can't hang up after a failed verification or a handoff.
- **"Today" comes from the server:** the authorise reply includes the India date (demo-clock aware), so "next Friday" becomes a date the promise rule accepts.
- **DOB never stored in the audit log:** `tool_events` shows `"dob": "[redacted]"`.
- **Call token must be used within 10 minutes** of authorisation; a token works for one Vapi call only.
- **Calling-hours switch (Saim):** hours rule turned off for testing with `calling_hours_enabled` (same pattern as attempt limits); back on for the demo story.
- **Functions pinned to Oregon:** Supabase runs a function nearest the caller (Mumbai from India) unless the `x-region` header says otherwise; Vapi, the test page and the smoke test all send `x-region: us-west-2`.
- **Call cap 2 → 4 minutes (Saim):** a full call (verify → dispute → promise) was cut off at 2:05.
- **Allowed browser origins** for `calls-api` are a setting (`CORS_ALLOWED_ORIGINS`), localhost for now; the Vercel address is added at go-live.

### Bugs found and fixed

- **Zod 4 treats a missing `arguments` key as invalid:** it would have rejected a whole tool-call request; made optional, test added.
- **Cloud bundler ignored the shared import map:** fixed via `import_map` per function in `supabase/config.toml`.
- **Hand-written constant-time compare:** replaced with Deno's standard `timingSafeEqual` (security rule: no custom crypto).
- **Server code wasn't format-checked by the gate:** added `fn:fmt` (Deno fmt) to `npm run check`.
- **My own clock check was wrong:** Git Bash showed UTC as "IST"; the server correctly blocked the 20:07 IST call. The smoke test now sets the demo clock, so it runs at any hour.

3. No announcing a tool result before it arrives (prompt rule) — **only partly works**, see M3 backlog.
4. Hand over on the first request for a person, in any language.
5. Tool latency: lighter database client + functions pinned to Oregon → webhook **~0.5 s from India** (was 2.2–2.7 s in calls).
6. Greeting "Hi, this is Asha" (was heard as "Marsha"); per-language silence line via Vapi hooks (the old setting was ignored per call).
