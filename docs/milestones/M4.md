## Plan

**Branch:** `feature/M4-whatsapp-core` · **Time box:** 4 h · **Status:** approved 2026-11-02 (STOP 1: Saim said "start building M4", all recommendations; brain prompt text still needs his approval) — building · **Then:** M5 (reminder loop), CP2 after M5

### Goal

Srinivas runs his credit book from WhatsApp. He texts the Meta test number and the bot answers from the real ledger built in M3. He can see who owes money ("pending", "closed", "Ramesh"), add credit ("Ramesh 5000, due 15th") and mark payments ("Ramesh paid 2000"). Every change goes through a confirmation card with buttons, and **nothing is saved until he taps Save**. Fixed commands are handled in code. Anything else goes to the Sarvam LLM, which can only *suggest* a change, never make one (ADR-0014).

### Acceptance criteria (SPEC §17 M4 = §6.1–6.3 by text)

- A **webhook spike** passes first: Saim's WhatsApp message reaches our function (Decision 1)
- Only the owner's number gets answers; others get one polite "not registered" reply
- Every Meta request's signature is checked; each message is handled once; Meta gets its answer at once
- **Ledger:** "pending" (top 10, biggest first, days overdue), "closed" (paid off this month), "<name>" (balance, last 5 entries, last promise, open claims)
- **Add credit / mark paid by text** → confirmation card [Save] [Edit] [Cancel]; unclear name → pick list; new name → "Add as new shopkeeper?"; missing due date → 15 days, shown on the card; cards expire after 30 min
- **Claims:** a payment Asha recorded as "claimed" can be confirmed by the owner [Confirm received] [Not received] (Decision 7)
- **Brain:** Hindi, Telugu, English and mixed messages; Sarvam LLM for anything the rules can't parse; Gemini if Sarvam fails; "Sorry, I didn't get that" + help if both fail
- **Done when:** Saim does the smoke-test script below on his phone and the database matches

### How one message works (new in M4)

```
Saim's WhatsApp ──► Meta ── POST /whatsapp-webhook (signed with the App Secret) ──► whatsapp-webhook
   check signature → 200 to Meta at once → work continues in the background:
   owner? ─ no ─► "This number is not registered" (once per number per day)
     │ yes
   seen this message id? ─ yes ─► stop (Meta retried)
     │ no
   button tap? ──► run the card action (Save / Edit / Cancel / pick / Confirm received …)
   fixed command? ("pending", "closed", "Ramesh", "Ramesh paid 2000", "Ramesh 5000 due 15th", help)
     │ no
   Sarvam LLM → one JSON suggestion (Zod-checked) ─ fails ─► Gemini ─ fails ─► "Sorry…" + help
   suggestion = read? ─► answer from the ledger      suggestion = change? ─► confirmation card
whatsapp-webhook ── POST graph.facebook.com/…/messages ──► reply / buttons / list on Saim's phone
```

*Webhook = the web address Meta calls each time a message arrives. Signature = a code Meta computes from the message and our shared App Secret, so a fake message can't pass.*

### Decisions

#### Decision 1: Webhook spike first: does Meta deliver Saim's messages to an unpublished app?
🔍 The Meta console warns that unpublished apps get only the dashboard's *test* webhooks, "including from app admins, developers or testers". Meta's docs don't settle it: they say the `messages` test webhook works in development mode, but say nothing clear about real messages. Until it's proven, nothing else is built on it.
📊 **Spike (≤ 30 min, ₹0):** a throw-away function that answers Meta's verify check and logs incoming messages (sender masked). I give you the Callback URL and verify token; you paste them in **Step 2 → Configure Webhooks** and subscribe to `messages`. You send "hi" to the test number.

| Result | What happens |
|---|---|
| Message arrives | ✅ Go. Build M4 as planned |
| Only the dashboard test arrives | **Publish the app** (Meta's "Live" switch). Needs a privacy-policy link (I add `PRIVACY.md` to the repo and give you its GitHub link) and an app icon/category. No card, no business verification expected. You click Publish; we retry |
| Publishing is blocked | I stop and come back to you with what Meta asks for |

✅ **My recommendation:** run it exactly like this, before any other M4 code.

#### Decision 2: An access token that doesn't expire — ⚠️ your step in Meta
🔍 The token in `.env` lasts ~24 hours; the bot would go silent tomorrow.
📊 **Options:** (a) **System user token**: in Meta Business Settings → Users → System users, add one, give it the app and the WhatsApp account, and generate a token with `whatsapp_business_messaging` + `whatsapp_business_management` and **Never expire**. You paste it into `.env` (10 min) · (b) regenerate the 24-hour token before each session.
✅ **My recommendation:** (a), at the start of M4. I'll walk you through it with screenshots, as with the test number.

#### Decision 3: How the brain works (ADR-0014)
📊 **Options:** (a) **code first, then one JSON answer from the LLM**: fixed commands are parsed in code; anything else goes to Sarvam `sarvam-105b` with a short prompt and must return exactly one JSON "suggestion" (`ledger_query`, `add_credit`, `mark_paid`, `help`, `unknown`), checked by Zod · (b) let the LLM call tools in a loop.
✅ **My recommendation:** (a).
📐 **Reasoning:** one LLM call per message (fast, cheap, easy to test), and the LLM never touches the database. Every change still needs the owner's Save tap, so a wrong guess costs a Cancel, never a wrong balance. If Sarvam errors, times out (8 s) or returns bad JSON → the same prompt goes to Gemini → if that fails too, "Sorry, I didn't get that" + help. Each message stores which path answered it (button / command / sarvam / gemini / failed), so M7's evals can measure it. **The brain prompt is your decision:** I show you the full text during the build, before it's used (like Asha's prompt in M3).

#### Decision 4: Confirmation cards
📐 A card is a WhatsApp message with buttons, saved as a `pending_actions` row: what will be saved, a 30-minute expiry, status open/saved/cancelled/expired. The buttons carry the card id, so a tap on an old card does nothing harmful ("This card has expired, send it again").

| Button | Does |
|---|---|
| **Save** | Writes the entry once (a second tap says "already saved"), then replies with the new balance |
| **Edit** | Closes the card and says "Send the corrected line, e.g. *Ramesh 5000 due 20th*" |
| **Cancel** | Closes the card, saves nothing |

Example card: *"Add credit · Ramesh (Ramesh Kirana) · ₹5,000 · due Sun 15 Nov · Balance after: ₹13,500 · [Save] [Edit] [Cancel]"*. Payments work the same way; part payments are fine; a payment bigger than the balance is allowed but the card warns "more than he owes (₹8,500)".
✅ **My recommendation:** as above. A new message while a card is open doesn't cancel it; each card stands alone until it expires.

#### Decision 5: Finding the right shopkeeper
📐 Names are matched to the 100 shopkeepers by name and shop name, ignoring case and small typos. Telugu or Hindi script ("రమేష్", "रमेश") goes through the LLM, which writes the name in English letters first.
- **One clear match** → card.
- **Several** (two Rameshes, a near miss) → a WhatsApp list of up to 10, showing name, shop and area → tap one → card.
- **No match** → "Add *Suresh* as a new shopkeeper?" [Yes] [No]. Yes creates him with his name only; shop, area and language default to the owner's (Anantapur, Telugu), and he gets a fake phone number in the never-real range. Then the credit card follows.
✅ **My recommendation:** as above. The new-shopkeeper details are editable later on the dashboard (M6).

#### Decision 6: Who may talk to the bot
📊 **Options:** (a) compare the sender with `OWNER_WHATSAPP_NUMBER` held as a function secret; the real number is never written to the database · (b) store it in `owners.whatsapp_number`.
✅ **My recommendation:** (a). Keeps the only real personal data out of the database and git. Message rows store the sender as a hash (a one-way code), never the number. A stranger gets one polite reply a day, and nothing else is read or written.

#### Decision 7: Confirming payment claims — pull forward from M5?
🔍 SPEC §6.3 (in M4) describes the owner confirming claims; SPEC M5 lists "claims confirm" too. Claims already exist from M3 calls (Ramesh's ₹2,000).
📊 **Options:** (a) **M4**: "Ramesh" shows open claims with [Confirm received] [Not received]; Confirm turns the claim into a confirmed payment, Not received marks it rejected (M5 gives that to Asha's next call) · (b) wait for M5, where the post-call WhatsApp summary sends these buttons automatically.
✅ **My recommendation:** (a). It reuses the card buttons (~20 min), completes §6.3, and M5 only has to *send* the same buttons after a call.

#### Decision 8: Reply language
📊 **Options:** (a) the bot **understands** Telugu, Hindi and English now, and **replies** in the language of the owner's message, using a small phrase table (~25 lines per language). Figures are always in digits · (b) understand all three, reply in English until M6 (voice notes).
✅ **My recommendation:** (a). For a Sarvam pitch, a Telugu question with a Telugu answer matters. ⚠️ Telugu and Hindi phrases need the same native-speaker check as Asha's greeting.

#### Decision 9: Plumbing
📐 Signature checked on the **raw** body in constant time (bad → 401, nothing read). Meta gets `200` at once and the work continues in the background (Supabase `EdgeRuntime.waitUntil`). That avoids Meta's retries on slow LLM replies. Message ids are stored with a unique rule, so a retry is skipped. New tables: `wa_messages` (id, direction, type, path, command, sender hash) and `pending_actions`. RLS on, no browser access, as in M3.

### Plain-English notes (for the pitch)

- **Why buttons before saving:** the owner's money book is the one thing the bot must never get wrong. The AI only suggests; the owner's tap saves.
- **Why rules before AI:** "pending" or a button tap is answered instantly and for free. The AI is used only when it's needed, so it stays fast and cheap, and every path is measured.
- **Data stays in India:** WhatsApp messages land on our Mumbai function, the AI is Sarvam's (India), and the only real personal data (the owner's number) never enters the database.

**Deviations**

- No separate spike function (agreed in the task brief): the real webhook is the spike.
- Bot data access is a second interface, `BookRepository` (`_shared/db/book-repository.ts`), instead of growing M3's `Repository`, so each stays small. `dues.ts` now exports `toPaise`, `toRupees`, `byOldestFirst` (reused by `cleared.ts`).
- `pending_actions.status` has a fifth value, `done`, for a pick list or "new shopkeeper?" step that has led to the next card (the plan listed open/saved/cancelled/expired).
- `pending_actions.kind` is `entry` / `pick` / `new_shopkeeper`; buttons carry ids only (`c:<card>:save`, `cl:<entry>:ok:<lang>`, `lk:<shopkeeper>:<lang>`). Claim buttons act on the claimed ledger entry directly (no card row), guarded by "only while still claimed".
- A new shopkeeper's **shop name = his name** (the owner's business name would break the `unique (owner_id, shop_name)` rule on the second new shopkeeper); area = owner's city (Anantapur), language = owner's (Telugu). Phones: `+91 00000 9xxxx` (seed uses 00001–00100), random, not unique.
- Save does "card open → saved" first, then the ledger insert; if the insert fails the card goes back to open and the owner is asked to tap Save again.
- A bare word that is not a shopkeeper ("thanks") is not trusted as a lookup and goes to the LLM.
- Sender hash = HMAC-SHA256 keyed with `META_APP_SECRET` (no extra secret). Rotating the App Secret changes the hashes.
- Outgoing replies are logged in `wa_messages` too (direction `out`, Meta's message id, type), best effort.
- Button taps and voice notes reply in the language saved on the card / in the button id; anything without one (an unknown button, a voice note) uses the owner's language (Telugu).
- `listEntries` reads the book in pages of 1,000 (the API's row cap; the book has ~2,200 entries), at most 20 pages.
- Voice notes and images get "text only for now" (voice notes are M6).
- `@std/crypto` is not available to Node scripts, so the smoke script signs and hashes with `node:crypto` (same algorithms).

**Known gaps**

- Not deployed and never run against Meta or the real database. The Meta POST path is tested only with a fake fetch.
- Brain prompt v1 and the Hindi/Telugu phrases are drafts (Saim; native speaker).
- Score band in "pending" (SPEC §6.1) waits for M5's scores; "last call note" in the lookup waits for M5 notes.
- The dashboard link for "and N more" waits for M6.
- Meta delivers retries of the same message id after a 200 only in rare cases; the handle-once rule covers them, but two different messages arriving at the same moment are handled in parallel by separate workers (no ordering guarantee between them).
- Stranger replies to numbers outside Meta's test-recipient list fail at Meta (logged as `whatsapp_send_failed`, code 131030 expected).
