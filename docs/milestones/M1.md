# M1 — Voice Spike (English + Hindi)

> One file per milestone: **Plan** (approved at STOP 1) on top, **Results** (STOP 2) below.

## Plan

**Branch:** `feature/M1-voice-spike` · **Time box:** 45 min · **Status:** ✅ done — results below

### Goal

Prove the voice stack works before building anything on top of it: a real browser call to a Vapi assistant in **English** and **Hindi/Hinglish**, with interruptions handled and latency measured. No tools, no database, no real collections logic yet — a short "hello, I'm the Suvidha assistant" conversation.

This is a **spike**: its main output is evidence (what works, what doesn't, which settings to use), recorded in an ADR.

### Acceptance criteria (from SPEC M1)

- 1-minute call works in English and in Hindi from the browser
- Interrupting the agent mid-sentence makes it stop and listen
- Latency measured and recorded
- Gemini-as-agent-model question answered (works / doesn't / fallback used)
- Findings and chosen settings recorded in ADR-0007

### Decisions

#### Decision 1: How the agent uses Gemini
🔍 **Ambiguity:** Vapi's docs don't clearly confirm a built-in Gemini option with our own key.
📊 **Options analysed:**
  (a) Vapi's built-in Google provider with our Gemini key saved as a Vapi credential — simplest if supported
  (b) Gemini's OpenAI-compatible endpoint via Vapi's "custom LLM" option — documented route, works with any compatible model
  (c) Vapi's own default model — works for sure, but every call spends free credit on the model too
✅ **My decision:** try (a) → if it fails, (b) → only then (c).
📐 **Reasoning:** (a) and (b) keep model cost on the free Gemini tier, so Vapi credit only pays for voice minutes. Whichever works is recorded in ADR-0004 (moves from Proposed to Accepted).
⚠️ **Override?** Tell me if you disagree; otherwise I proceed with this.

#### Decision 2: One assistant for both languages, or two
🔍 **Ambiguity:** English and Hindi need different speech recognition and voice settings.
📊 **Options analysed:**
  (a) Two assistants (`collections-en`, `collections-hi`) generated from one config — clear, but two things to publish and keep in sync
  (b) One assistant; language-specific speech settings and greeting applied when the call starts — one thing to publish
✅ **My decision:** (b)
📐 **Reasoning:** one config, one publish, one eval target later. The customer's preferred language is known before the call starts, so the browser passes the right settings. If Vapi rejects the per-call settings, fall back to (a).
⚠️ **Override?** Tell me if you disagree; otherwise I proceed with this.

#### Decision 3: Which speech providers to test for Hindi
🔍 **Ambiguity:** Hindi and Hinglish (mixed) quality differs by provider.
📊 **Options analysed:**
  - **Speech-to-text:** Deepgram Nova-3 (multilingual — better for Hinglish mixing) vs Azure `hi-IN` (pure Hindi)
  - **Voice:** Azure Indian neural voices — `en-IN` (Indian English) and `hi-IN` (Hindi) — natural accents, low cost
✅ **My decision:** test **both** speech-to-text options in Hindi with the same script; keep Azure Indian voices; pick the winner by evidence.
📐 **Reasoning:** Hinglish is how real borrowers talk; choosing by test result, not by assumption, is the point of a spike.
⚠️ **Override?** Tell me if you disagree; otherwise I proceed with this.

## Results

**Branch:** `feature/M1-voice-spike` · **Decision record:** `docs/adr/ADR-0007-voice-stack.md` · **Date:** 2026-11-01

### Result

✅ **The voice stack works.** Real browser calls in English, Hindi and Hinglish, with interruptions, silence handling and replies starting in about **1.2 s**. One major change from the plan: the live agent runs on **Vapi-hosted `gpt-4.1-mini`**, not Gemini (Gemini's free tier was overloaded and too slow; evidence in ADR-0007).

### Acceptance criteria

| Criterion (SPEC M1) | Status | Evidence |
|---|---|---|
| 1-minute call works in English and Hindi from the browser | ✅ | English 75–90 s, Hindi 71 s (Azure), Hinglish 88 s (Deepgram) |
| Interrupting the agent makes it stop and listen | ✅ | 3–6 interruptions per call, all honoured |
| Latency measured and recorded | ✅ | English 1.15–1.27 s, Hinglish 1.26 s average reply (Vapi call metrics) |
| Gemini-as-agent-model question answered | ✅ **Doesn't work** | No reply in 20 s; 503/429 from Google; 2.5-flash 3–5 s. Fallback: Vapi-hosted GPT (Saim's choice) |
| Findings and settings recorded in ADR-0007 | ✅ | ADR-0007 accepted; ADR-0004 amended |

### Smoke test (Saim, real voice in Chrome)

| # | Test | Result | Notes |
|---|---|---|---|
| 1 | English call | ✅ 1.1–1.3 s replies | Natural; stays on "test call" script as instructed |
| 2 | Hindi · Deepgram (Hinglish) | ✅ 1.26 s | Mixed script transcript; Asha replied in natural Hinglish |
| 3 | Hindi · Azure | ✅ works, 2.4 s | Slow because of 1.5 s end-of-speech wait → cut to 0.8 s for Hindi |
| 4 | Hinglish mixing | ✅ | Deepgram `multi` clearly better than Azure |
| 5 | Interruption | ✅ | Stops within ~0.2 s of the caller speaking; maybe too eager — revisit in M3 |
| 6 | Silence | ✅ | "Are you still there?" once, then ends on its own, no error shown |

**Credit used:** $0.65 (9 calls, 8.8 minutes). Model cost per call ≈ $0.001–0.002; most of the cost is Vapi's platform fee.

### Decisions taken during the milestone (Saim)

1. Live agent model → **Vapi-hosted `gpt-4.1-mini`** (over Gemini 2.5 Flash or our own Gemini proxy).
2. Hindi end-of-speech wait → **0.8 s** (English stays 1.5 s).
3. Hindi speech-to-text → **Deepgram `multi`**; Azure option removed. The page now offers **English** and **Hindi**.
4. Call cap stays **2 minutes**, including on demo day.

### Problems hit → fixes

| Problem | Cause | Fix |
|---|---|---|
| Blank page: "Vapi is not a constructor" | SDK is CommonJS; the dev server returns `{ default: Vapi }` | `resolveVapiClass()` handles both shapes + test |
| Agent never replied | Gemini free tier: no response / 503 / 429 | Switched model (ADR-0007) |
| Every transcript line shown twice | SDK's `removeAllListeners()` removes nothing; React StrictMode's first subscription stayed attached | Remove each listener by name + StrictMode-cycle test. First attempt (timestamp de-duplication) was wrong — Vapi sends no timestamp — and was removed |
| Red error banner at normal call end | SDK reports "Meeting has ended" as an error | Treated as a normal hang-up + test |
| Hindi replies 2.4 s | Vapi waited the full 1.5 s on unpunctuated Hindi transcripts | Per-language end-of-speech wait (Hindi 0.8 s) |
| Test page unreachable | App stopped the idle dev server | Restarted; dev server no longer reloads the page when coverage files change (a reload would drop a live call) |

How the duplicate bug was found: a short real call in the app's browser pane with a silent fake microphone, tapping the SDK's events — it showed one message from Vapi but two listeners on the page.
