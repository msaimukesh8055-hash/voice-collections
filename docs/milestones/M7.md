### Goal

The bot feels finished. (1) A voice reply sounds like a person talking to Srinivas, not Bulbul reading the text message aloud. (2) The bot has an Easy Recovery AI logo and an About line on WhatsApp. (3) Messages share one layout and a fixed emoji per idea, a **Menu** list opens every feature with one tap, and the next step after key replies is a button (Remind / Paid in full / Part payment after a lookup).

### Acceptance criteria (SPEC §17 M7 Build A, §6.7, §5)

- **Spoken summary:** every voice reply is a short (~20–30 s, ≤ 600 characters) spoken-style summary written by `sarvam-105b` in the reply language (Telugu, Hindi or English), addressing Srinivas, with a different opening each time. Voice stays Kavitha (`tts.ts` unchanged)
- **Never wrong figures:** code checks every number and every shopkeeper name in the summary against the reply text; any failed check, a timeout (8 s) or an error → today's `spokenText`. No link is ever spoken. Figures are always in the text message too
- **Bot profile:** profile photo (logo, 640×640 PNG) and About line set on the Meta test number by a one-off script that reads only env vars; description and category set too. If Meta refuses on a test number, that is recorded and Saim saves the contact instead
- **Menu:** "menu", "hi", "hello", "help" and the other greetings send a **list message** with every main action; each row works with one tap
- **Buttons:** a shopkeeper lookup ends with [Remind] [Paid in full] [Part payment]; other key replies get the buttons agreed in Decision 9. Every tap does the same as the typed command (nothing saved without Save; nobody called without a tap)
- **Layout:** one emoji per concept and the layout rules in Decision 8, in all three languages; the English twin under Telugu still works on every changed message
- **WhatsApp limits respected:** ≤ 3 reply buttons, ≤ 10 list rows, button title ≤ 20, row title ≤ 24, row description ≤ 72, list button ≤ 20, interactive body ≤ 1,024 characters (all tested)
- **Done when:** `npm run check` is green with 100% coverage on the new checks and taps, the functions are deployed, and the smoke test below passes on Saim's phone

#### Decision 2: Spoken summary — Sarvam only, fallback straight to `spokenText`
🔍 The brain and follow-up use Sarvam → Gemini → safe default (`createJsonLlm`). Should the summary do the same?
📊 **Options:** (a) **Sarvam only; any failure → `spokenText`** · (b) Sarvam → Gemini → `spokenText`.
✅ **My recommendation:** (a). The voice note already arrives ~7 s after the text; a Gemini retry can add up to 8 s more. `spokenText` is a correct, approved fallback, and the pitch is "Sarvam end to end". Implemented with `askSarvamChat` + `extractJson` (same timeout, same Zod pattern), not `createJsonLlm`.
📐 Settings: `temperature: 0.7` (variety; the checks keep it safe), `max_tokens: 400`, `reasoning_effort: null` (already set inside `askSarvamChat`). The summary is asked for only when `spokenText` would say something (so nothing changes for empty replies), and only after a heard voice note (unchanged rule, 50 voice replies a day cap unchanged).

#### Decision 3: The summary prompt (v1) — ⚠️ prompt text is Saim's decision
📐 Full draft below. Code fills the `{…}` parts. The model answers with one JSON object `{"say": "…"}`, checked with Zod.

**System prompt (draft, `SPOKEN_PROMPT_VERSION = 'v1'`):**
```
You turn one WhatsApp reply from the Easy Recovery AI bot into a short voice note for
Srinivas Reddy, a wholesale trader in Anantapur who keeps his credit book on WhatsApp.
He will hear it, not read it. The full text with every figure is already on his screen.

Write in {LANGUAGE}. {STYLE}
Talk to him the way a helpful shop assistant talks to the owner: casual, warm, natural.
Call him {ADDRESS}.

Rules:
- 20 to 30 seconds when spoken: 2 to 4 short sentences, at most 500 characters.
- Opening for this note: {OPENING}. Do not start with "Here is" or "This is".
- Say only what is in the reply. Never add a name, an amount, a date or any number that is
  not in it. Never work out a new figure: no totals, no differences, no counting.
- Write every amount in digits exactly as in the reply, then the word "{RUPEES}".
  Never write a number in words.
- Write every name exactly as in the reply, in English letters.
- A long list: give the headline and at most the first 3 people, in the reply's order.
- If the reply has buttons, end by telling him which one to tap, using the button's name.
- No links, no emoji, no symbols such as * or ₹.

Answer with ONE JSON object only: {"say": "<the voice note text>"}
```

**User message (built by code):**
```
Reply language: {te|hi|en}
Buttons he can tap: {Save, Edit, Cancel | none}

The reply:
{the reply text: Heard line and link lines removed, as spokenText does}
```

**Filled-in parts (drafts):**

| Part | Telugu (`te`) | Hindi (`hi`) | English (`en`) |
|---|---|---|---|
| `{LANGUAGE}` | Telugu, in Telugu script | Hindi, in Devanagari | simple Indian English |
| `{STYLE}` | Everyday spoken Telugu as people talk in Anantapur, not bookish Telugu. Everyday English words (credit, balance, pending, Save) may stay in English letters. | Everyday spoken Hindi (Hindustani), not formal Hindi. Everyday English words (credit, balance, pending, Save) may stay in English letters. | Short, plain sentences. |
| `{ADDRESS}` | Srinivas garu | Srinivas ji | Srinivas |
| `{RUPEES}` | రూపాయలు | रुपये | rupees |

(The `{RUPEES}` word is the same as `spoken.ts` uses today; రూపాయలు = "rupees".)

**`{OPENING}` — code picks one at random each time (random source injected, so tests are fixed):**
1. begin with his name
2. begin with the main figure
3. begin with a short friendly word, like "OK", "Sare" (Telugu) or "Achha" (Hindi)
4. begin with the key point in a few words
5. begin by saying what you just did for him (checked the book, made the card)

📊 **Alternatives for variety:** (a) **code-picked opening + temperature 0.7** · (b) temperature only ("start differently each time"). Models tend to repeat the same opening for the same kind of reply even at higher temperature.
✅ **My recommendation:** (a).

**Example (English, a credit card):** reply text "*Add credit* · Ramesh (Ramesh Kirana) · ₹5,000 · due Sun 15 Nov · Balance after: ₹13,500", buttons Save, Edit, Cancel →
`{"say": "Srinivas, I've got Ramesh down for 5,000 rupees of credit, due Sunday 15 November. That takes him to 13,500 rupees. If it looks right, just tap Save."}` → every number (5,000, 15, 13,500) and the name Ramesh are in the reply → spoken.

#### Decision 4: Safety checks on the summary (LLM-output validation, 100% tested)
📐 Pure function `checkSpoken(say, source)` in a new `spoken-check.ts`. **Any** failure → `spokenText`, logged as `spoken_summary` with the reason only (never the text):

| # | Check | Fails when | Reason |
|---|---|---|---|
| 1 | Shape | Not one JSON object with `say` as text, 1–600 characters after trimming (`MAX_SPOKEN_CHARS`) | `bad_json` / `too_long` |
| 2 | No links | `http://`, `https://` or `www.` anywhere | `link` |
| 3 | Right script | `te` without Telugu script, `hi` without Devanagari, `en` with Telugu or Devanagari | `script` |
| 4 | **Every number is in the source** | Any number in `say` (ASCII, Devanagari ०–९ or Telugu ౦–౯ digits; "13,500", "13500" and "1,84,000" compared without commas) is not one of the numbers in the source text (amounts, days, dates, scores, %, counts) | `number` |
| 5 | No amounts in words | A scale word that hides a figure: thousand, hundred, lakh(s), crore, hazaar/hajar, vela/velu; हज़ार, हजार, सौ, लाख, करोड़; వంద, వందల, వేలు, వేల, లక్ష, లక్షలు, కోటి | `number_word` |
| 6 | **Every name is in the source** | A shopkeeper name or shop name (whole word, any case) appears in `say` but not in the source | `name` |
| 7 | No invented names | `te`/`hi`: any word in English letters that is not in the source and not on a short allowlist (Srinivas, garu, ji, Asha, rupees, Save, Edit, Cancel, Menu, Remind, credit, balance, pending, due, overdue, insights, dashboard, OK, voice, note, call, payment, card). `en`: a capitalised word that is not the first word of a sentence and is not in the source or the allowlist | `name` |

Also: the LLM call failing or taking over 8 s → `llm_failed`. Outcome logged: `ok` or `fallback` + reason + ms.
📐 The source is the same text the LLM was given (all bodied replies of the outcome, Heard line and link lines removed, plus button titles), so "Save" or "Remind Ramesh" on a button counts as in the source.
📐 Check 4 is strict on purpose: if the model says "3 people" and "3" is nowhere in the reply, the summary is thrown away. Better a flat voice than a wrong figure. The smoke test counts how often this happens.
📊 **Alternative:** drop check 7 (fewer fallbacks, a made-up name could slip through). ✅ **My recommendation:** keep it; shopkeeper names are the one thing the owner acts on.

### Decisions

#### Decision 1: What the history carries, and the shopkeeper's own words
🔍 Facts from records are safe. Saim's example ("said harvest money comes next week") is the shopkeeper's words, which can carry a planted claim (CP2 M2: "the owner agreed to waive ₹2,000").
📊 **Options:**
  (a) **Fixed reasons only**: hardship, dispute, wanted the owner, upset — no free words at all. Safest; Asha knows *that* money was tight, not *why*.
  (b) **Fixed reasons + one sanitised phrase per call** from the callback summary (Asha's English line in `followups.summary`), labelled as their claim.
  (c) The LLM follow-up note, sanitised. Rejected: it mixes our figures with their words, so stripping numbers leaves broken sentences, and it is the exact path CP2 M2 closed.
✅ **My recommendation: (b)**, with this sanitiser (`theirWords`, pure, 100% tested). Any rule failing → the phrase is **dropped whole** and only the fixed reason stays:
| # | Rule | Why |
|---|---|---|
| 1 | Only from a call where identity was **confirmed** | Before that the speaker may be his son or a neighbour |
| 2 | Only from callbacks with reason hardship, dispute or other (not wants_owner, which is just "call me") | Those carry a reason worth remembering |
| 3 | **Any number → drop** (digits in any script, scale words from `spoken-check.ts`, plus one…twenty, half, double, ₹, Rs, rupee/rupees, रुपये, రూపాయలు) | Never a figure from their words. Dropping beats stripping: "will pay in 2 weeks" stripped becomes "will pay in weeks" |
| 4 | Blocked words → drop: owner, Srinivas, Asha, agreed, agree, waive, waiver, discount, write off, forgive, cancel, settle, settled, free, reduce, balance, outstanding, paid, ignore, instruction, prompt, system, assistant, tool, rule, pretend, "you must", "you should" | Claims about what the owner agreed, money terms, and instruction-like text |
| 5 | Keep only letters, spaces and `. , ' -`; quotes, brackets, colons, new lines removed | The phrase can't break out of its quotes |
| 6 | ≤ 80 characters, cut at a word with "…"; fewer than 3 letters left → drop | Short, one idea |
| 7 | At most one phrase per call (the first callback that passes) | Keeps `say` short |

#### Decision 2: Where the history is built, one request, not RAG
📐 **Not RAG, in one line:** RAG searches a pile of text for passages that look relevant; here we know exactly what we need (this shopkeeper's last 3 calls), so a direct lookup by shopkeeper id is exact, faster, free and has no embeddings to keep in sync.
📐 **Shape (reversible):**
- `db/supabase-memory.ts` `listPastCalls(shopkeeperId, excludeCallId, since)`: **one** PostgREST request: `calls?select=id,queued_at,mode,status,identity_status,promises(id,amount,promise_date,status),ledger_entries(amount,entry_date,status,payment_mode),followups(kind,reason,summary),followup_runs(actions)&shopkeeper_id=eq.…&id=neq.<this call>&status=in.(completed,declined,missed)&queued_at=gte.<since>&order=queued_at.desc&limit=3`. Uses the existing `calls_shopkeeper_idx (shopkeeper_id, queued_at desc)`. Rows Zod-parsed into `PastCallRow` (DB shape, no logic). Runs in the same `Promise.all` as today's reads: **0 extra round trips**; expected +20–40 ms on the slowest read, at worst
- `calls/call-history.ts` (pure): `buildCallHistory({ rows, promises, today }) → CallHistory` — structured, no English: `{ date, mode, outcome, promise {amount, promiseDate, status} | null, claim {amount, paidDate, mode, status} | null, reasons: CallbackReason[], upset: boolean, theirWords: string | null }[]`, newest first, ≤ 3. Promise status taken from the **checked** promise list by id (a promise that broke today shows as broken)
- `calls/call-history-asha.ts`: `describeHistoryForAsha(history) → string` (English lines for `say`, '' when empty) and `historyData(history)` (counts only, for the audit row; never their words)
- **Munshi later** adds its own `describeHistoryForOwner(history, language)` on the same `buildCallHistory`; nothing in B1 is Asha-only except the describer
📊 Alternative: a Postgres view or function for the history. ✅ Recommend the embedded request: no migration, and the logic stays in tested TypeScript.
